# 判断材料 — 建物の窓テクスチャを共有アトラス化するか（2026-07-30）

**結論（先に）**: 技術的には確実にできる。ただし得られる削減は**窓辺で−60コール（約3%）・歩行で−90コール（約12%）**にとどまる。発熱の主因に対しては中くらいの効き。**今すぐやるより、実機で発熱を確かめてから判断する**のが得。実装はしていない（承認記録2のとおり調査まで）。

---

## 1. いまどうなっているか（実測）

窓のテクスチャは `src/engine/town3dViewer.js` の `makeWinTex()`（601行〜）が作っている。

- **128×128のキャンバス**に、コンクリの微細なムラ・雨だれの汚れ・サッシ枠・十字桟・窓台まで描いている
- 窓割りは4種（`winGrids` ＝ 3×4・2×3・4×4・3×3）。昼用4枚＋灯り用4枚の**計8枚**が元になる（680・683行）
- 建物1棟ごとに、位置ハッシュで4種のどれかを選び、**`clone()` して `repeat` をその建物の寸法から決める**（1882〜1888行）
  - `rep = round(幅/2.6)` ・ `repV = round(高さ/2.4)` ＝ 建物ごとに違う値

**GPUのメモリは増えていない。** `clone()` は絵の実体（Source）を共有するため、460棟あってもGPUに載る絵は増えない（`renderer.info.memory.textures` は情景を10往復しても102枚のまま。→ #3の実測）。

**増えているのは描画コールのほう。** 区画統合は「同じ区画・同じ材質・**同じ絵**」のメッシュを1つに束ねる。建物ごとに絵の識別子が違うので、窓つきの壁は**仲間が1枚もいない束**になり、統合対象から外れる。

```
■ 区画統合の内訳（__town3dMerge）
   区画メッシュ: 86
   元メッシュ: 657
   走査メッシュ: 1159
   絵柄あり: 460
   取りこぼし: 502
   取りこぼし束: 487
   区画: 86
   削減: 571
```

**取りこぼし502枚 ÷ 487束 ＝ 1束あたり1.03枚**。つまり取りこぼしのほぼ全部が「単独の壁」で、そのうち460枚が窓テクスチャつき。**残った取りこぼしの92%が、この件そのもの**。

## 2. 共有化したらどれだけ減るか（実測にもとづく見込み）

`PORT=4890 node scripts/qa-wintex.mjs`（新規）で、画面に実際に描かれている「窓テクスチャつきの壁」を状態別に数えた。

```
■ 窓辺（眺める・既定）: 画面に描かれる物=1821（種類 422） 描画コール=1834
   建物の壁（窓テクスチャつき）: 80個（19種類）← 共有化すれば区画統合に載る候補
   その他の絵つき: 184個 / 絵なし: 1557個

■ 低空飛行（街の中心）: 画面に描かれる物=1517（種類 332） 描画コール=1528
   建物の壁（窓テクスチャつき）: 91個（11種類）← 共有化すれば区画統合に載る候補
   その他の絵つき: 143個 / 絵なし: 1283個

■ 着地して歩く: 画面に描かれる物=747（種類 214） 描画コール=756
   建物の壁（窓テクスチャつき）: 120個（21種類）← 共有化すれば区画統合に載る候補
   その他の絵つき: 79個 / 絵なし: 548個
```

共有化すると、これらは「区画×窓割り4種」に畳まれる（画面に映る区画はおおむね5〜8）。

| 状態 | いまのコール | 壁の枚数 | 統合後の見込み | 削減見込み |
|---|---|---|---|---|
| 窓辺（既定の眺め） | 1834 | 80 | 約20 | **−60（−3%）** |
| 低空飛行 | 1528 | 91 | 約24 | **−67（−4%）** |
| 着地して歩く | 756 | 120 | 約30 | **−90（−12%）** |

**いちばん効くのは歩いているとき**。いちばん長く見る窓辺では3%にとどまる。

## 3. 絵はどれだけ変わるか

**理屈のうえでは変わらない。** やることは「テクスチャ側の `repeat` をやめて、同じ倍率を壁のUV（テクスチャの貼り位置）に焼き込む」だけで、貼られる絵も繰り返し回数も同一。

ただし確認が要る箇所が3つある。

1. **面取りした近景の建物**（`RoundedBoxGeometry`・1893行）は箱とUVの作りが違う。焼き込みの式をそのまま当てられるか要確認
2. **夜と夕方の窓灯り**（`emissiveMap`）も同じ倍率で貼っている。昼と灯りで窓割りがズレると「窓の位置に灯りが来ない」破綻になる（既存コードは `wvi` で揃えてある。同じ対応が要る）
3. **壁の継ぎ目**。`repeat` は端数を丸めずに繰り返すが、UV焼き込みでも同じ端数になるかを画素差で確かめる

検証は今回作った `scripts/qa-mergescenes.mjs`（統合あり/なし＋アニメの床値）がそのまま使える。

## 4. 工数と危なさ

- **工数: 中**（半日〜1日）。`house()` のUV焼き込み・面取り箱の対応・灯り側の同時対応・夜/夕の見た目確認
- **乱数の順序は壊れない**。`clone()` と `repeat` は `R()` を消費していない（1886行に「旧来ここでR()を使っていた分を保つ」空打ちがある）。UVを触るだけなら街の生成は不変
- **危ないのは絵のほう**。窓が伸びる・ズレる・灯りが窓と合わない、が起きうる。必ず画素差とスクショで確認する

## 5. 戻し方

`?nomerge=1` は**統合を止めるだけ**で、UVの焼き込みは戻らない。実機で見比べるには**専用のキルスイッチが別に要る**（例: `?winuv=0` でいまの `repeat` 方式に戻す）。実装するならこれも一緒に入れる。

## 6. おすすめ

**いまはやらない。** 理由は3つ。

1. 得られる削減が、いちばん長く見る窓辺で**3%**。発熱の主因（画面に重ねる合成層とコール総数）に対しては中くらいの効き
2. 今回の7コミットをまだ実機で確かめていない。**実機で「まだ熱い」と分かってから**、効き目の大きい順にやるほうが無駄がない
3. 絵が壊れる余地がある変更なので、他に絵の変更を抱えていないときに単独でやるほうが安全

**やるとしたらの順番**: 実機確認 → まだ熱い → 歩行・低空の体感が重い → そのときにこれ（歩行−12%）。
